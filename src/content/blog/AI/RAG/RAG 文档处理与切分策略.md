## RAG 文档处理与切分策略

### 一、为什么文档处理会影响 RAG 效果

RAG 的检索质量首先取决于知识库中的内容是否被正确解析和组织。LLM 只能看到最终送入上下文的文本，Embedding 模型也只能处理传给它的内容。如果原始文档在上传、解析、清洗或切分阶段丢失了结构，后续的向量检索和答案生成都无法完整恢复这些信息。

文档处理不是简单的格式转换，而是把 PDF、网页、数据库记录等异构数据转换成可检索、可过滤、可追溯的知识单元。每个环节都会影响最终的召回结果：

| 环节 | 典型问题 | 最终影响 |
| --- | --- | --- |
| 文件上传 | 文件伪造、大小超限、编码混乱或内容不完整 | 解析器崩溃、任务失败或文档内容缺失 |
| 格式校验 | 扩展名与实际 MIME 类型不匹配，或选择了错误的解析器 | 文档解析错误，后续流程拿不到有效文本 |
| Layout 解析 | PDF 多栏阅读顺序错误、表格合并单元格、页眉页脚混入正文 | 结构丢失、语义错位和上下文关系被打乱 |
| 清洗去噪 | 乱码、特殊字符、重复空行、目录和页眉页脚残留 | 噪声进入索引，Embedding 表达失真 |
| Chunking | 语义截断、上下文断裂、块过大或过小 | 召回不准、证据不完整或上下文过长 |
| Metadata | 未保存来源、页码、版本、时间和权限信息 | 无法过滤、定位来源和生成可靠引用 |
| 入库 | 向量维度不一致、重复写入或超过 Token 限制 | 索引写入失败、数据重复或检索结果异常 |

其中，PDF、扫描文档和表格尤其需要关注结构恢复。多栏文档如果按照错误的阅读顺序提取，原本相邻的内容可能被拆散；表格如果只提取成连续文本，行列关系和表头信息可能丢失；OCR 如果识别错误，错误文本还会被继续写入索引，影响后续所有查询。

因此，文档入库前应建立可观测的处理流程，至少记录原始文件、解析结果、清洗结果、切分结果和入库状态，并通过抽样检查确认文本顺序、表格结构、来源信息和权限字段都符合预期。**Embedding 模型和向量数据库只能处理输入内容，无法替代文档解析，也无法修复已经丢失的结构。**

### 二、文本切分策略：把长文档变成可检索单元

文本切分（Chunking）是文档进入 Embedding 和向量库之前的关键环节。它的目标，是把长文档拆成边界清晰、语义相对完整、大小适合检索的文本单元。切分结果会直接影响召回准确率、上下文完整性、输入 Token 成本和答案质量。

![RAG 文本切分策略选型对比](../../../../assets/blog/AI/RAG/RAG%20文档处理与切分策略/1.png)

#### 1. 固定长度切分：适合作为基线

固定长度切分只需要设置 Chunk 大小和重叠窗口。例如，每 1000 Token 切分一个 Chunk，相邻 Chunk 重叠 200 Token。这种方式实现简单、行为稳定、容易压测，适合短文档、FAQ 和结构相对简单的知识库。

它的局限也很明确：切分器只关注长度，不理解段落、表格、代码块和章节边界。一段完整的规则可能被切成两半，导致单独召回时缺少前提或结论。因此，固定长度切分适合作为评测基线，最终参数应通过固定的文档集和问题集验证，而不是直接套用其他项目的配置。

例如，下面这段退货规则如果恰好在 1000 Token 边界处被切开：

> 除以下情况外，均可申请七天无理由退货：（一）定制商品；（二）鲜活易腐商品；（三）在线下载的数字化商品……

前一个 Chunk 可能只保留“除以下情况外，均可申请七天无理由退货”，后一个 Chunk 则从“（一）定制商品”开始。单独检索任意一个 Chunk，模型都可能缺少完整规则。

#### 2. 递归字符切分：优先保留自然边界

递归字符切分（Recursive Character Splitting）按照一组有优先级的分隔符逐层处理文本。它通常优先保留文档、章节和段落边界，只有当前片段超过目标大小时，才继续使用句子、空格或字符进行细分。

这种策略比单纯按字符数切分更符合自然语言结构，适合技术文档、产品手册、研究报告和 Markdown 内容。LangChain 的 `RecursiveCharacterTextSplitter` 就采用了类似思路。

递归切分的参数需要结合语料类型设置。代码和配置文件可以使用较小的 Chunk，并按函数、类和代码块保留结构；普通文本通常需要更大的 Chunk，以保证一个完整段落能够被一起召回。参数应以 Token 或模型实际输入长度为准，不能只按字符数估算。

#### 3. 语义切分：按内容相关性组织 Chunk

语义切分先计算句子或段落之间的相似度，再将连续且主题相近的内容归入同一个 Chunk。它关注的是语义边界，而不是固定的字符数或标题边界，适合主题切换明显、段落长度差异较大的文档。

语义切分需要额外生成句子或段落的 Embedding，因此会增加处理时间和调用成本。为了避免产生过小的片段，通常需要设置 `min_chunk_size`，并对 Chunk 的最小长度、最大长度和异常分布进行检查。实际使用时，可以先从 200～400 Token 的候选范围开始，再通过召回率、上下文完整性和小 Chunk 占比调整参数。

#### 4. 按文档结构切分：优先使用天然边界

结构化文档通常已经包含可用的语义边界，应优先利用标题、章节、段落、列表、表格和代码块进行切分：

| 文档类型 | 推荐切分方式 | 常见实现思路 |
| --- | --- | --- |
| Markdown | 按 H1、H2、H3 标题逐级切分 | 保留标题路径和章节层级 |
| HTML | 按标题、段落和语义标签切分 | 处理 h1～h6、p、div 等标签 |
| PDF | 按页面、章节或版面结构切分 | 结合 Layout 解析和页码信息 |
| 代码 | 按函数、类、模块和代码块切分 | 保留文件路径、语言和符号信息 |
| 论文与报告 | 按章节、段落和表格切分 | 保留章节路径、表格标题和脚注关系 |

结构切分可以减少语义被截断的概率，但页面边界不一定等于语义边界。对于 Word 导出的简单 PDF，按页切分的收益可能有限；对于金融报告、法律文书等版面结构稳定的文档，Layout 解析和章节切分通常更有价值。最终方案应通过业务问题集比较，而不是默认页面切分一定更好。

#### 5. Parent-Child Chunk：兼顾召回粒度与上下文完整性

向量检索需要较小的单元来区分相近主题，LLM 生成又需要足够完整的上下文。Parent-Child Chunk 将这两个目标分开处理：子 Chunk 用于向量索引和精确召回，父 Chunk 用于补充上下文。

例如，可以将约 300 Token 的子 Chunk 写入向量索引，同时记录它所属的约 1200 Token 父段落。查询先命中子 Chunk，再根据父子关系取回父段落，既能提高召回定位能力，也能减少答案缺少上下文的问题。父 Chunk 的大小、关联范围和存储成本需要与召回效果一起评估。

#### 6. 重叠控制：连接相邻 Chunk 的边界

重叠（Overlap）用于保留相邻 Chunk 之间的上下文联系，尤其适合连续叙述、长段落和跨句规则。重叠过小，关键信息容易在边界处断开；重叠过大，重复内容会增加索引规模、输入 Token 和检索噪声。

重叠比例不应固定套用。普通文本可以从 512 Token 的 Chunk、50～100 Token 的重叠开始建立基线；代码优先按函数和类切分；法规合同优先保留条款、款项和完整法律效力单元；表格则尽量保持表头、行列关系和说明文字完整。之后根据召回率、证据完整性、重复召回率和成本进行调整。

文本切分没有适用于所有知识库的唯一参数。实际工程中，应先建立固定的评测集，比较不同策略对召回率、上下文完整性、答案正确率、延迟和成本的影响，再确定默认配置。

### 三、什么是语义丢失，为什么会发生？

语义丢失，指原始文档里的关键信息在解析、清洗、切分或入库时被削弱，导致检索结果只剩下零散文字，原本的条件、顺序和关联关系却不见了。

Embedding 模型接收到的只是当前 Chunk。跨段、跨页的条件没有放在同一个 Chunk 中，标题、章节路径和表格关系没有写入元数据，向量表示就会缺少这些信息。检索命中之后，LLM 只能根据残缺的上下文作答。

#### 1. 结构被切断

一条完整的业务规则可能被切到两个 Chunk 里。第一个 Chunk 讲“申请条件”，第二个 Chunk 讲“审批流程”，中间的关键条件“满足 X 时还需要提供 Y 材料”被切在边界上。两个 Chunk 单独召回时都像是完整片段，合在一起却缺少决定结论的那句话。

#### 2. 上下文蒸发

Chunk 保留了正文，却丢失了它在原文中的位置。模型读到“过去三年中……”时，可能无法判断这句话描述的是某个供应商的风险评估，还是某位客户的历史交易，因为标题、父章节或前文背景没有一并保留下来。

#### 3. 表格结构被打散

多行多列的表格如果被解析成一段连续文本，行列之间的关系就会消失。主键、从属关系、数值和属性可能重新排列，检索虽然能命中关键词，答案却无法正确对应到表头和具体行。

#### 4. 专有名词被切坏

产品名、内部缩写、接口名和版本号往往不能按普通文本处理。例如“SSO 单点登录”被切成“SSO 单点……”，Embedding 后的词片段与查询中的完整术语无法稳定匹配，最终表现为检索结果中明明存在相关文档，系统却召回不到。

#### 5. 如何减少语义丢失

首先，优先保留文档原有的结构。标题路径、页码、段落编号、表格标题、文件路径和版本号都应写入 Metadata；对于存在明确层级的内容，切分时应把父标题和必要的上下文带入 Chunk。

其次，根据文档类型选择切分方式。业务规则、法规和合同应尽量保留条款及其完整条件；表格要保留表头、行列关系和说明文字；代码要按函数、类和模块切分。页面本身构成自然语义单元时可以按页保留，但页面切分不应成为所有 PDF 的默认方案。

查询侧也可以增加补救措施，例如为 Chunk 生成摘要或可能对应的问题，帮助“钱怎么退”这类口语查询匹配到“退款申请路径”这样的文档表达。摘要和问题变体只能扩大检索入口，最终仍应回到原文证据中完成回答，并通过评测集确认是否真的提升了召回效果。

在预算允许的场景，可以考虑 Late Chunking：先让模型对较完整的文档进行编码，再在保留上下文信息的基础上切分和池化。它能够减少 Chunk 独立编码带来的上下文损失，但计算成本更高，适合文档规模可控、对语义检索质量要求较高的场景。

对于复杂文档，还可以使用 Contextual Chunking，让模型或规则为每个 Chunk 补充章节路径、文档主题和局部背景，再进行向量化。这种方式对嵌套表格、混合图文和跨章节引用更有帮助，但需要额外的处理成本和质量校验。

语义丢失的判断应回到具体问题：检索结果是否包含回答问题所需的条件、对象、时间和来源。只看向量相似度不够，必须同时检查证据完整性和最终答案是否引用了正确上下文。

### 四、结构丢失：不同文档类型的处理策略

结构丢失通常发生在解析阶段。原始文件看起来内容完整，转换成文本后却可能失去阅读顺序、标题层级、表格关系和页面上下文。切分和 Embedding 只能处理已经提取出来的内容，因此应先恢复结构，再决定 Chunk 怎么切。

#### 1. PDF 多栏与版面混淆

很多 PDF 只保存字符、字体和坐标信息，并不保存可靠的阅读顺序。普通提取器如果按照物理坐标直接读取，双栏文章可能被横向串读，跨栏表格可能被拆碎，页眉、页脚和页码也可能混入正文。

处理 PDF 时可以按以下方式组织流程：

1. **使用版面感知解析器**：先识别文本块、图片、表格和阅读顺序，再输出逻辑上的内容流。MinerU、Marker、Docling 以及基于 Layout 模型的方案都可以作为候选，具体选择取决于文档类型、部署环境和表格复杂度。
2. **过滤页面噪声**：结合页眉、页脚、页码和装订线的位置规律进行区域过滤。固定模板文档可以使用规则，版式变化较大的文档则需要结合版面检测结果，避免误删正文。
3. **单独处理表格区域**：检测到表格后，交给 Table Transformer、PP-Structure、PaddleOCR-Table 等表格提取模块，尽量还原为 HTML、Markdown 或结构化 JSON。表格直接降级成连续纯文本后，行列关系通常很难恢复。

#### 2. Word 标题层级与上下文断裂

Word 文档经常存在“看起来像标题、实际上没有使用标题样式”的情况：用户用加粗、字号和空行模拟层级，解析后只剩一串段落。子小节一旦脱离父标题，代词、业务概念和适用范围就容易失去指向。

处理这类文档时，可以先读取 OOXML 中的样式信息，再结合字体大小、段前段后间距、编号规律和关键词推导标题层级，重建 H1、H2、H3 文档树。python-docx 适合读取 Word 结构，Mammoth 适合将 Word 转换为更接近 HTML 的语义结构；对于格式不规范的历史文档，仍需要启发式规则和人工抽样检查。

切分时应优先使用标题边界和完整段落作为基础单元。某个章节过长时，再在同一层级内部继续切分，而不是直接从全文按固定字符数截断。每个 Chunk 还应保留章节路径，例如：

Metadata: {"breadcrumb": "技术规范 > 数据接口 > 鉴权机制"}

也可以在向量化前给正文加上父标题，让检索结果同时携带文档主题和当前段落的范围。

#### 3. Excel 字段错位与主从关系丢失

Excel 的核心信息存在于二维甚至多维的表格关系中。逐行转换成纯文本后，表头只出现一次，后续数据行就不再知道每个数值对应哪一列；合并单元格和多级表头还会进一步放大这个问题。

更稳妥的处理方式包括：

1. **扁平化多级表头**：对合并单元格进行前向填充，将“年度、季度、指标”等层级合并成完整字段名，例如“年度_季度_指标”。
2. **将每一行转换为自解释结构**：用 JSON 字典或键值对文本保存一行数据，让每个切片都携带完整字段名，而不是只保留制表符分隔的值。例如：{"日期": "2024-01-01", "项目": "研发投入", "金额": "100万"}。
3. **隔离混合版面**：财务表格上方的说明文字、表格主体和下方附注应分别识别，再路由到文本解析器或结构化表格处理器。

#### 4. 扫描件与 OCR 识别漂移

扫描件的风险不只在于“识别不出来”，还包括识别结果看似正常但关键字符已经发生变化。例如 0 和 O、1 和 l、8 和 B 容易混淆，表格边框虚化会导致行列错位，低分辨率图片还可能让段落换行被误删或误加。

高价值文档可以采用分层校验：

1. **选择合适的 OCR 方案**：根据文档复杂度评估传统 OCR、版面感知 OCR 或视觉语言模型。复杂表格和混合图文可以测试 GOT-OCR、Nougat、DeepSeek-VL 等方案，但仍要用业务样本验证，不应只依据模型名称选择。
2. **双引擎交叉比对**：合同、发票和财务报表可以同时运行两个 OCR 引擎，例如 PaddleOCR 与云端 OCR 服务，对关键字段的差异进行标记，再结合上下文复核。
3. **做数值和业务规则校验**：用正则检查日期、金额和编号格式，用业务规则检查总计是否等于子项之和、日期范围是否合理。校验失败的内容应回到原图重新识别，而不是直接写入向量库。

处理结构化文档时，优先级应当是“恢复结构、保留关系、再做切分”。当解析结果无法回答几个简单的原文核对问题时，继续调整 Embedding 模型通常没有帮助，应该先回到版面解析、表格抽取和 OCR 校验环节排查。

### 五、如何处理多模态内容？

真实知识库里通常不只有文本，还包括图片、流程图、表格、音频和视频。只把这些内容旁边的文字抽出来，知识库会丢掉相当一部分信息。将多种模态一起纳入检索和生成的方案，通常称为 Multimodal RAG，也就是 MM-RAG。

多模态 RAG 的关键不在于把所有内容都转换成同一种向量，而在于保留原始内容、结构化描述、时间或页码等定位信息，并让不同模态的检索结果能够在回答阶段重新对齐。

#### 1. 三种常见架构

**文本代理法**先把非文本内容转换成文本，再复用成熟的文本 RAG。图片和图表可以使用视觉语言模型生成描述并配合 OCR，音频和视频可以通过 ASR 生成带时间戳的字幕。这个方案接入成本低，现有的向量库、BM25 和 Rerank 都可以继续使用，适合先把系统跑起来。它的代价是转换过程会损失空间布局、图表走势、音色和画面动作等信息。

**跨模态统一嵌入法**使用联合表征模型，把文本、图片或音频映射到同一个语义空间。用户输入文本后，可以直接检索相关图片、音频片段或视频帧。CLIP、SigLIP 和 ImageBind 属于这类方案的代表。它能保留一部分非文本特征，但对密集文字、复杂表格和长文档的理解通常不如专门的文本检索，因此常需要和 OCR、字幕或结构化描述结合。

**视觉原生法**直接把页面截图或场景图像作为检索对象，减少对 OCR 和复杂版面解析的依赖。ColPali 一类方案会为页面生成更细粒度的多向量表示，检索命中后再把原始页面交给多模态模型回答。它对复杂表格、技术图纸和扫描文档更有价值，但向量数量、存储和推理成本都更高，部署前需要评估吞吐量与预算。

实际项目通常采用混合方案：文本描述、OCR、字幕负责可解释的关键词检索，跨模态向量负责补充语义召回，原始图片或音视频则作为最终证据交给多模态模型。

#### 2. 图片、流程图和数据图表

图片在文档中的作用不同，处理方式也应区别对待。装饰性图片可以只保存来源和简单描述，承载信息的图片则需要保留原图和结构化索引。

1. **自然图片**：生成全局描述、对象标签和必要的 OCR 文本，分别建立文本索引和图像向量索引。命中后返回原图，而不是只把描述文本交给模型。
2. **流程图和架构图**：让视觉模型提取节点、边、方向和关键文字，保存为 JSON、Mermaid 或 PlantUML 等结构化表示，同时保留原图。结构化结果便于回答“上游依赖谁”“故障经过哪些节点”等关系问题，原图则用于核对布局和细节。
3. **折线图、柱状图和财务图表**：不要只保存一句摘要。应尽量提取标题、坐标轴、单位、时间范围、图例和具体数据，转换为 Markdown 表格或 JSON。只有这样，系统才能回答具体数值、比较变化和计算趋势。
4. **表格图片**：先进行表格区域检测和结构恢复，再生成 Markdown 或 JSON；表格所在章节、标题、单位和时间范围应作为上下文一起保存。

#### 3. 音频的切分与对齐

音频处理的目标不是得到一整段转写文本，而是建立“谁在什么时间说了什么”的可检索记录。

1. 使用 VAD 根据自然停顿和语音活动切分，避免在句子中间按固定秒数截断。
2. 使用说话人分离（Diarization）标记发言人，并在转写结果中保留 speaker、start、end 和 text 字段。
3. 保留足够精确的时间戳，例如 speaker=A、start=02:15、end=02:45。回答引用音频内容时，前端可以直接跳转到对应时间段。
4. 对会议、访谈和培训音频补充主题、章节和参与者等 Metadata，方便按会议名称、发言人和时间过滤。

音频 Chunk 的长度需要同时考虑语义完整性和定位精度。过短会让观点被拆散，过长则会降低检索定位能力；实际参数应结合说话人变化、停顿和问题类型评估。

#### 4. 视频的多轨道处理

视频至少包含视觉流、伴音流和画面文字流，三者需要在时间轴上对齐：

1. **伴音流**：通过 ASR 生成带时间戳的字幕文本，并标记说话人。
2. **视觉流**：使用场景切换检测识别镜头边界，再为每个镜头提取代表性关键帧，减少大量重复画面的索引成本。
3. **文字流**：对 PPT、白板、字幕、标牌和演示界面进行 OCR，保存文字出现的时间范围。
4. **复合片段**：将同一时间窗口内的关键帧、字幕和 OCR 文本绑定成一个 Video Segment，再生成描述该片段动作和主题的摘要。

例如，一个培训视频片段可以同时保存“讲师解释接口鉴权”的字幕、“白板上的调用流程”关键帧，以及画面中出现的接口名称。查询命中后，系统既能返回文字答案，也能给出视频的起止时间和关键帧作为证据。

#### 5. 多路召回与多模态重排

单独使用文本或图像检索都容易漏掉信息。更稳妥的做法是根据查询类型走多路召回，再统一排序：

1. **文本路径**：用文本 Embedding 检索图片描述、OCR 文本、音频字幕和视频摘要。
2. **跨模态路径**：用跨模态 Embedding 直接检索图片、音频或视频关键帧。
3. **关键词路径**：用 BM25 等方法检索产品名、接口名、专有名词、数字和字幕原文。
4. **结果合并**：对不同路径的分数做归一化和加权，去除重复片段，并保留来源、页码、帧号或时间戳。
5. **多模态重排**：先召回候选结果，再使用能够同时读取文本和视觉内容的重排模型或视觉语言模型，让它根据用户问题重新比较候选图片、表格和关键帧的相关性。

#### 6. Prompt 组装与来源追踪

检索结果交给多模态模型时，应尽量保留原始文档的图文顺序。图片不应统一堆在 Prompt 末尾，字幕、图表说明和对应图片应放在同一条证据附近，模型才能理解它们之间的关系。

每条证据至少应携带文档名、页码或章节、资源 ID，以及音视频的起止时间。生成答案时要求模型输出来源，例如图片页码、表格名称或视频的 04:12～04:35 时间段，前端就可以直接跳转、定位和回放。

#### 7. 方案选型建议

| 场景 | 推荐方案 | 重点关注 |
| --- | --- | --- |
| 密集扫描文档、财务报表、技术图纸 | 视觉原生或视觉解析与文本检索结合 | 页面理解、表格恢复、向量存储和推理成本 |
| 会议录音、培训视频、访谈资料 | ASR、关键帧和 OCR 的时间对齐 | 转写质量、场景切分、时间戳和跨轨道关联 |
| 电商图片、产品相册、设计素材 | 跨模态向量检索与多模态重排 | 图片语义、文本标签、对象细节和重复图片 |

多模态 RAG 的验收标准也应覆盖不同模态：文本问题要检查召回段落，图表问题要检查数值和单位，音频问题要检查说话人和时间戳，视频问题要检查关键帧与字幕是否属于同一时间窗口。只有把检索结果和原始证据绑定起来，系统才具备真正可核验的多模态回答能力。
